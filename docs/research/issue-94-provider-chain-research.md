# Issue #94 — Preliminary provider-chain source research

**Status:** preliminary, nonbinding options only. **Research date/access date:** 2026-10-08. This is a public-document review, not a provider evaluation or coverage audit. No metadata API endpoint was queried; no credentials, paid endpoints, user/paper content, or source-document content were used. Provider-published API ceilings below are not proposed product budgets.

## Summary

Public first-party documentation supports a small set of distinct options for later, baseline-driven evaluation: OpenAlex as a broad metadata/location graph; DataCite as a DOI registry complement for research outputs and explicit version relationships; OpenAIRE Graph as an aggregator of publication/repository/research-output metadata; and PubMed/PMC as a biomedical specialist. Semantic Scholar offers useful paper-ID and batch APIs, but its current public license wording appears not to authorize an ordinary product-resolution integration without an expanded license. These are roles to evaluate, **not a selected provider set or ordering**; neither #86’s baseline gate nor human approval of choices, disclosures, and budgets is satisfied. ([Issue #94](https://github.com/arrokh/paper-t-rail/issues/94); [Issue #86](https://github.com/arrokh/paper-t-rail/issues/86))

## Approved cross-run consent constraint

[ADR 0020](../adr/0020-require-matching-consent-for-provider-output-reuse.md) settles one shared policy: a successor may reuse a historical external-provider output only when its consent snapshot for that provider exactly matches the originating run's snapshot, including provider identity, authorized data categories, and recorded retention disclosure. Missing or changed consent makes the output incompatible; new outbound work requires explicit successor consent. This is necessary but not sufficient: stage-specific compatibility still applies. A cache hit must independently pass the requesting run's authorization checks. This rule does not select providers or settle cache keys, not-found versus transient-error handling, provider-specific disclosures, budgets, or the full consent design.

## Findings

### 1. OpenAlex — broad metadata and version/location graph candidate

- **Explicit coverage/type evidence:** OpenAlex describes a database of aggregated information about public scholarly publications, drawn from external platforms. Its controlled vocabulary explicitly distinguishes books, book chapters, conference papers/abstracts, preprints, datasets, software, dissertations, reference entries, and other types. However, the current vocabulary page warns that recently introduced `book-review`, `conference-abstract`, `conference-paper`, `data-paper`, and `software-paper` types have low or zero coverage during rollout. The work-type vocabulary is mapped from multiple upstream taxonomies and derives from Crossref’s types; its location provenance includes Crossref, DataCite, PubMed, and repository harvests. **Inference:** it may add normalization, merged records, and locations beyond a direct Crossref lookup, but it is not independent of Crossref or its upstreams. None of this is a measured coverage result for Paper T-Rail’s bibliography. ([OpenAlex Terms of Service, last revised 2026-10-02](https://openalex.org/OpenAlex_termsofservice.pdf); [Work types, last updated 2026-08-17](https://help.openalex.org/data/work-types/); [Locations, last updated 2026-09-18](https://help.openalex.org/data/locations/))
- **Identifiers and versions:** A work has an OpenAlex ID and may map DOI, MAG, PMID, and PMCID. The work’s DOI field is described as the published-version DOI when more than one DOI exists. Separate locations can record `submittedVersion`, `acceptedVersion`, or `publishedVersion`, and may represent publisher, repository, or preprint copies. These are useful distinctions, not proof every edition or manuscript version is represented correctly. ([Work attributes, last updated 2026-10-07](https://help.openalex.org/data/works/attributes/); [Locations, last updated 2026-09-18](https://help.openalex.org/data/locations/))
- **API/configuration/reliability:** Basic queries can be made without a key; OpenAlex recommends a free API key for usage at scale and accepts it in either an `Authorization` bearer header or `api_key` query parameter. Published limits include a $1/day free usage allowance, 100 requests/second, `per_page` up to 100, and up to 100 OR values per filter; `429` also signals daily-budget exhaustion. Paid tiers exist but are outside this research and are not approved. Its Terms say the service may change or be withdrawn, data may be incomplete/out of date, and the service is not guaranteed to be continuously available. ([API authentication, last updated 2026-08-19](https://help.openalex.org/api/authentication/); [Pricing, last updated 2026-08-11](https://help.openalex.org/access/pricing/); [Terms of Service, last revised 2026-10-02](https://openalex.org/OpenAlex_termsofservice.pdf))
- **Trust/data boundary/retention:** OpenAlex’s privacy policy says request logs include “the full request address (which contains your search terms and filters),” API key, IP address, client/browser, status, and credits used; it says logs and analytical copies are deleted after 90 days, with aggregate counts retained. Thus a title or other query term would be visible in request logging under this policy. Use of a bearer header rather than a key in the URL is supported, but does not prevent logging of the query. Separately, the policy says some text-processing features send user-supplied text to AI-model providers, including semantic-search queries and reranking inputs containing the query and top-result title/source/year/type. This is a distinct feature path; check exact endpoint behavior rather than assuming it applies to every metadata lookup. ([Privacy Policy, last revised 2026-10-03](https://openalex.org/OpenAlex_privacy_policy.pdf); [API authentication, last updated 2026-08-19](https://help.openalex.org/api/authentication/))
- **Trade-off:** The most broadly typed and version/location-explicit option reviewed, but not a completeness guarantee; new type categories have acknowledged gaps, source records inherit upstream variation, and the provider logs query terms. There is also a legal wording issue to resolve: OpenAlex pricing documentation says the data is released under CC0, while its Terms prohibit unauthorized reproduction, modification, distribution, or republication of its Data/Database without prior written consent. This report does not reconcile the scope of those statements; legal review is needed before deciding on persistence or redistribution. ([Pricing, last updated 2026-08-11](https://help.openalex.org/access/pricing/); [Terms of Service, last revised 2026-10-02](https://openalex.org/OpenAlex_termsofservice.pdf))

### 2. DataCite — DOI registry complement, especially datasets/software and version relations

- **Explicit coverage/type evidence:** The unauthenticated public API is for retrieving/searching DataCite DOI metadata and returns only DOIs in `Findable` state, excluding draft and Registered/non-Findable records. Search supports fields such as title, creator, related identifiers, resource type, version, and related items. DataCite’s schema includes resource categories such as `Dataset`, `Software`, and `Preprint`; that establishes schema support, not the proportion of any discipline/reference type in the registry. ([DataCite REST API, documentation updated 2026-09-25](https://support.datacite.org/docs/rest-api); [Query DOI metadata, updated 2026-08-07](https://support.datacite.org/docs/queries); [Software citation and reuse, updated 2026-09-30](https://support.datacite.org/docs/software-citation-and-reuse))
- **Identifiers and versions:** Records are DOI-centered. The versioning guidance recommends reusing/updating a DOI for minor changes, and assigning a new DOI for major changes with `IsNewVersionOf` / `IsPreviousVersionOf` links; `HasVersion` / `IsVersionOf` can link a canonical DOI to specific versions. The guidance says individual stewards determine what counts as major. The query schema also exposes `relatedItems.edition`, but the reviewed sources do not establish comprehensive book/chapter coverage. ([Versioning, updated 2026-09-22](https://support.datacite.org/docs/versioning); [Query DOI metadata, updated 2026-08-07](https://support.datacite.org/docs/queries))
- **API/configuration/reliability:** Public metadata retrieval/search requires no authentication. Published limits are 500 requests per five minutes per IP for unidentified requests, 1,000 per five minutes/IP for identified requests, and 3,000 per five minutes/IP for authenticated requests; excess returns `429`. DataCite recommends identifying frequent clients with a descriptive `User-Agent` and contact email and suggests incremental backoff. These are provider limits, not a product budget; the reviewed docs do not state an uptime commitment. ([DataCite REST API, updated 2026-09-25](https://support.datacite.org/docs/api); [Rate limits](https://support.datacite.org/docs/rate-limit))
- **Trust/data boundary/retention:** DataCite’s privacy policy says metadata and identifiers are reusable without restriction through public APIs/search interfaces, and that metadata consumers can omit credentials for public queries. It says typical **website visitor** request data (including IP address, browser, referrer, and time) is erased after seven days. It does **not** specify a separate API-query/log retention period or say whether query terms are logged. The policy says it took effect 2020-10-20 and may change; treat the age and scope of this evidence cautiously. An identified `User-Agent` or `mailto` also transmits the contact address by design. ([DataCite Privacy Policy, effective 2020-10-20](https://datacite.org/privacy-policy/); [Rate limits](https://support.datacite.org/docs/rate-limit))
- **Trade-off:** A natural optional lookup/search source for DOI-bearing datasets, software, preprints, and other deposited outputs, including explicit version relations; it is not a general-purpose substitute for a broad bibliographic index, and no Paper T-Rail coverage has been measured. ([DataCite REST API, updated 2026-09-25](https://support.datacite.org/docs/rest-api); [Versioning, updated 2026-09-22](https://support.datacite.org/docs/versioning))

### 3. OpenAIRE Graph — multi-source research-output/repository graph option

- **Explicit coverage/type evidence:** OpenAIRE’s Graph API identifies research-product categories `publication`, `dataset`, `software`, and `other`, plus data sources, projects, organizations, and persons; V3 filters include source and related entities. The provider describes the Graph as metadata aggregated from many scholarly resources. This is repository/graph aggregation, not a measured reference-resolution success rate or representative corpus. V4 is documented as beta; V3 is the currently recommended version. ([Research Products, documentation version 11.2.0](https://graph.openaire.eu/docs/11.2.0/apis/graph-api/research-products/); [V3 filtering, documentation version 11.2.0](https://graph.openaire.eu/docs/11.2.0/apis/graph-api/research-products/filtering); [Graph API overview](https://graph.openaire.eu/docs/apis/graph-api/overview/); [Graph production workflow](https://graph.openaire.eu/docs/graph-production-workflow/))
- **Identifiers and versions:** V3 exposes separate filters for an OpenAIRE internal product `id`, a persistent identifier (`pid`), and an identifier at the original source (`originalId`). Do not treat the returned OpenAIRE ID as a DOI or assume every product has a DOI. The reviewed V3 material does not establish a version/edition model equivalent to DataCite’s explicit version relations; confirm before relying on it for version-specific identity. ([V3 filtering, documentation version 11.2.0](https://graph.openaire.eu/docs/11.2.0/apis/graph-api/research-products/filtering))
- **API/configuration/reliability:** The official terms documentation (version 10.1.0) states free HTTPS access, up to 60 unauthenticated requests/hour or 7,200 authenticated requests/hour, and CC BY reuse with OpenAIRE attribution. Authenticated access uses a personal token. The same page says production APIs run 24/7, but the reviewed evidence is not an uptime SLA. The versioned terms/rate page may lag the current V3 documentation and should be rechecked before any implementation; no credentials were sought or used. ([Terms of use, documentation version 10.1.0](https://graph.openaire.eu/docs/10.1.0/apis/terms/); [Graph API overview](https://graph.openaire.eu/docs/apis/graph-api/overview/))
- **Trust/data boundary/retention:** The Graph privacy statement lists contributor metadata that can be processed: first/family/other names, identifiers such as ORCID, and affiliation. It states the purpose is to “Aggregate, curate, and disseminate scholarly metadata,” identifies a data processor for hosting, and gives retention as “As long as research products are publicly available.” It does not specify retention for API requester logs or query strings in the statement reviewed. ([OpenAIRE Graph Privacy Statement, date not displayed](https://graph.openaire.eu/policy))
- **Trade-off:** A plausible optional source if the baseline identifies repository/data/software records as a material unresolved subgroup. Its aggregation may overlap other providers and the published rate/terms page is versioned; coverage and operational reliability must be tested rather than inferred from the Graph’s scope. ([Graph production workflow](https://graph.openaire.eu/docs/graph-production-workflow/); [Terms of use, version 10.1.0](https://graph.openaire.eu/docs/10.1.0/apis/terms/))

### 4. Semantic Scholar — paper graph candidate, subject to license clearance

- **Explicit coverage/type and identifier evidence:** Academic Graph API documentation exposes paper, author, citation, and reference records. Paper lookups accept Semantic Scholar IDs and external identifiers including DOI, arXiv, PMID, PMCID, MAG, and ACL. Its documented publication-type filter includes journal articles, conference, book, book section, dataset, review, case report, clinical trial, and other categories. The batch paper endpoint accepts up to 500 IDs and a response up to 10 MB. These fields establish supported types/operations, not subgroup coverage rates; the reviewed public docs do not provide representative coverage denominators by field. No full version/edition lineage is established by the docs reviewed. ([Academic Graph API OpenAPI specification, accessed 2026-10-08](https://api.semanticscholar.org/graph/v1/swagger.json); [Academic Graph API docs](https://api.semanticscholar.org/api-docs/))
- **API/configuration/reliability:** The official API tutorial says an individual API key has a one-request-per-second rate across endpoints; no-key users share a pool affected by other clients. API docs/tutorial identify `429 Too Many Requests` and recommend an API key and batch endpoints. The API license does not guarantee uninterrupted availability or that results will be accurate, complete, or error-free. No key was obtained or used. ([API tutorial, date not displayed](https://webflow.semanticscholar.org/product/api/tutorial); [API license, date not displayed](https://api.semanticscholar.org/license/))
- **Trust/data boundary/retention and licensing:** The license defines “Input Data” as data supplied to call the API and warrants it will “only use Input Data for the sole purpose of providing a response” and will not share it with parties other than the Licensee or make it public. Separately, the license defines Usage Data to include visit/session/impression/click-through/clickstream data, allows monitoring, and permits aggregate/anonymized statistics to be made public. No fixed API-input or usage-data retention period was found in the license. Its stated ordinary grant is limited to internal, non-commercial research/education for ML training/evaluation or dataset transformation; it says uses outside that purpose, including commercial purposes, require an expanded license. **Inference:** routine product-side reference resolution is not clearly within the stated ordinary grant, so do not treat this as usable absent written license clearance. The API license page did not display a revision date when reviewed. ([Semantic Scholar API license, date not displayed](https://api.semanticscholar.org/license/))
- **Trade-off:** Strong identifier interoperability and batch lookup on paper, but the documented license fit is a material blocker, and no independent coverage or uptime evaluation was performed. The general Ai2 Privacy Notice is dated 2025-02-19 but describes Ai2 Sites/services broadly; it does not replace the API-specific license or establish API log retention. ([Semantic Scholar API license](https://api.semanticscholar.org/license/); [Ai2 Privacy Notice, last updated 2025-02-19](https://allenai.org/privacy-policy/2025-02-19))

### 5. PubMed / PubMed Central — biomedical specialist option

- **Explicit coverage/type evidence:** NLM describes PubMed as citations and abstracts in biomedical literature, including MEDLINE, PMC, and Bookshelf contributions. PubMed supports publication types and some preprint citations; NLM says individual conference abstracts are generally out of scope and that some preprints are included under specific arrangements. This is a domain supplement, not an all-discipline source. ([PubMed User Guide, last updated 2026-09-30](https://pubmed.ncbi.nlm.nih.gov/help/))
- **Identifiers and versions/full text:** PubMed/PMC use PMID and PMCID identifiers, with DOI available in records where supplied. PubMed is metadata/abstract discovery; PMC is the separate full-text repository. PMC OAI-PMH returns metadata for PMC items, but full text only for articles whose licenses/usage rights allow reuse (`set=pmc-open`); NLM directs automated retrieval to approved PMC services and requires article-level license checking. The reviewed material does not show a general cross-disciplinary edition/version resolver. ([PubMed Download Data](https://pubmed.ncbi.nlm.nih.gov/download/); [PMC OAI-PMH API, last modified 2026-08-20](https://pmc.ncbi.nlm.nih.gov/tools/oai/); [PMC text-mining policy](https://pmc.ncbi.nlm.nih.gov/tools/textmining/))
- **API/configuration/reliability:** NCBI’s E-utilities policy states no more than 3 requests/second absent an API key; the E-utilities manual documents a default 10 requests/second with a key. For distributed clients, NCBI asks for `tool` and `email` identification and recommends moving jobs exceeding 100 requests to weekends or 9pm–5am ET weekdays. PMC OAI-PMH separately limits calls to 3/second and disallows concurrent requests. These are distinct service limits; no combined product budget or API uptime SLA is inferred. ([NCBI scripting policies](https://www.ncbi.nlm.nih.gov/home/about/policies/); [E-utilities guide](https://www.ncbi.nlm.nih.gov/books/NBK25497/); [PMC OAI-PMH API](https://pmc.ncbi.nlm.nih.gov/tools/oai/))
- **Trust/data boundary/retention:** NCBI’s policy says it monitors site traffic for security and states it does not collect personally identifiable information about website visitors. The sources reviewed do not publish an E-utilities query-content/API-log retention period. NLM warns that although government-created webpage material is public domain, some resources contain third-party material and reuse rights must be checked; PMC full-text reuse is explicitly article-license dependent. ([NCBI policies](https://www.ncbi.nlm.nih.gov/home/about/policies/); [PMC OAI-PMH API](https://pmc.ncbi.nlm.nih.gov/tools/oai/))
- **Trade-off:** A well-documented candidate for biomedical references, PMID/PMCID matches, and legally eligible PMC text; its domain scope and PMC permissions make it unsuitable as a general fallback for broad disciplines. ([PubMed User Guide](https://pubmed.ncbi.nlm.nih.gov/help/); [PMC OAI-PMH API](https://pmc.ncbi.nlm.nih.gov/tools/oai/))

## Preliminary shortlist/options and trade-offs

These are **unranked roles for a later evaluation**, not an initial selected chain:

- **Broad index option:** evaluate OpenAlex against the #86 adjudicated baseline for identity resolution and version/location findings, particularly where its documented newly introduced types may be sparse. Its relationship to Crossref and query logging should be included in the trade-off review.
- **Complementary research-output registry:** evaluate DataCite for records whose bibliography entries identify dataset/software/preprint/other DOI outputs; its scope is registered, findable DataCite DOI metadata, not a general all-publications index.
- **Repository/graph option:** retain OpenAIRE as an optional comparison if #86 points to repository-aggregated, data/software, or project-linked records. Avoid assuming that graph size or service descriptions prove subgroup coverage.
- **Discipline-specific option:** retain PubMed/PMC only for the biomedical subgroup and only separate metadata discovery from license-eligible full-text acquisition.
- **Conditional option:** do not include Semantic Scholar in an implementable shortlist unless counsel/product approval confirms a license that covers this use. Its API license currently describes ordinary use more narrowly than a product resolution service.

**No provider order, final provider set, paid plan, cost/budget, key procurement, or user-document transfer is recommended or approved.**

## Contradictions and disputed evidence

- **OpenAlex reuse terms:** Its pricing docs say data is CC0, while its Terms of Service restrict unauthorized reproduction/distribution/republication of Data/Database without prior written consent. The wording may concern different scopes (data license vs use of the service/database); the sources reviewed do not resolve that. Treat redistribution/persistence rights as requiring human/legal review, not as a settled conflict or permission. ([Pricing](https://help.openalex.org/access/pricing/); [Terms](https://openalex.org/OpenAlex_termsofservice.pdf))
- **Semantic Scholar API use:** The API license’s ordinary-use scope appears restrictive for a product integration and says expanded licensing is needed for other uses. No alternate current API-specific written permission was reviewed. ([API license](https://api.semanticscholar.org/license/))
- No other direct contradictions were identified in the first-party material reviewed. Several important absences below are **unknowns**, not evidence that a provider does not log or retain data.

## Missing evidence / residual uncertainty

- No representative or adjudicated coverage figures for any provider across the target disciplines or reference types; no counts for identity precision, false matches, metadata-only outcomes, version choice, or full-text availability. This depends on #86.
- No live request measurements, service-health/SLA comparison, latency, outages, or validation that documented quotas remain stable. API limits cited are documentation statements, not observed service behavior.
- API-specific query logging/retention is not stated in the reviewed DataCite, OpenAIRE, PubMed/NCBI, and Semantic Scholar sources; OpenAlex gives more explicit query-log detail. No log-retention conclusion should be inferred from silence.
- DataCite’s privacy policy page is effective 2020-10-20; OpenAIRE rate/terms evidence is on documentation version 10.1.0; Semantic Scholar’s API license page did not show a revision date. Recheck current versions before approval.
- No determination of legal fit for the application’s persistence, display, attribution, or execution-artifact retention; no privacy impact assessment or provider-specific consent/disclosure text; no final provider-chain, cache-key, error-state, retry, or system-budget specification. ADR 0020 settles only the cross-run consent compatibility rule described above.
- Automated source-check tooling returned “unclear” for semantic verdicts; cited provider pages/policy text were manually inspected. This is not a legal opinion or API conformance test.
