# Keep Source Document storage behind an S3-compatible boundary

Paper T-Rail uses an endpoint-configured S3 client in the API and names the Compose service `object-storage`; Compose pins the tested local S3-compatible image because the prior public image became unavailable and the replacement passed the required SigV4 presigned-GET response-override contract. Other compatible services can be configured without changing application flows, provided they support the operations and response overrides documented in the storage configuration; the adapter currently uses static access/secret credentials rather than provider-specific identity modes. The configured bucket must already exist: the local Compose service provisions it, while external installations must provision it themselves, so runtime credentials need no bucket-list or bucket-create permissions. Any existing pre-migration object-storage volume has an incompatible on-disk format, so Compose neither declares nor mounts it and cleanup leaves it untouched; existing objects need an explicit S3-level copy and are not automatically migrated.
